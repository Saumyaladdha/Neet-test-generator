Section 01

Product Overview

A web application where NEET students upload their study material — textbook pages, handwritten notes, diagrams, formula sheets — and get a ready-to-attempt practice test generated from that content.

The student controls difficulty, question type, and how many questions they want — and can now mix several type/difficulty combinations into a single test (e.g. 5 easy MCQs + 3 hard Assertion-Reason questions, all in one test). Before generating, the system analyses the content and tells the student exactly what is possible, so they set expectations before the job runs.

Who uses it

NEET aspirants — Class 11 and 12 students preparing for the medical entrance exam.

What they upload

Images of textbook pages, handwritten notes, diagrams, formula sheets. Or a single PDF.

What they get back

A NEET-pattern practice test with MCQs, Assertion-Reason questions, and/or Match the Column questions (mixed freely within one test), with an answer key.

Two APIs, two jobs

The system is split into exactly two APIs because they have fundamentally different latency requirements:

  • Detector API — synchronous, fast, student waits. Analyses content, returns question count ranges. Unmetered — no daily limit consumed at this step.
  • Generator API — async, slow, student gets a progress screen. Generates the actual questions via SQS + ECS worker. Daily limit is enforced here.

Subjects supported today

Biology and Chemistry only. Physics is not yet built — adding it is a prompt-folder addition, not a code change (see Code Structure).

Section 03

test_id — the One ID

test_id is the single identifying concept used across the system, but it is not one ID shared across every table — each generate call mints its own.

Where generatedWhat it identifiesPrimary key of
POST /detectOne upload + detection resultNeetTestGenerator_Detector
POST /generateOne specific job/test (always a fresh id)NeetTestGenerator_Jobs and, once finished, NeetTestGenerator_Test
Why /generate never reuses the detection's test_id

One detection commonly feeds several generate calls — a student uploads one PDF, then asks for an easy test, then a hard test, then a mixed test, all from the same upload. If every one of those jobs reused the detection's own test_id as its primary key, the second generate call would silently overwrite the first job's row in DynamoDB before either finished processing — this was found and fixed during E2E testing.

The fix: /generate always mints its own new test_id. The originating detection's id is passed in as source_test_id and stored on the job purely for traceability — it is not the primary key.

Client flow:
  1. POST /detect                    → returns test_id = "detect-A"
  2. POST /generate {source_test_id: "detect-A", components: [...]}
       → server mints a NEW test_id = "job-1"  (this is the real test)
  3. POST /generate {source_test_id: "detect-A", components: [...]}  (different combo)
       → server mints a NEW test_id = "job-2"  (a second, independent test)

  job-1 and job-2 both have source_test_id = "detect-A", but are otherwise
  completely independent rows — neither can overwrite the other.
Section 04

Detector API

Analyses the uploaded content and returns how many questions of each type and difficulty can be generated from it. The frontend uses this to show the student a slider range before they request generation, and the Generator API later validates each requested component's count against these same ranges.

Synchronous No SQS Unmetered SSE Heartbeat

Inputs

user_id       string    required
subject       string    required   biology / chemistry
medium        string    required   english / hindi
files         multipart required   images OR one PDF
file_type     string    required   image / pdf

S3 Upload Structure

Images:
  neetTestGenerator/{user_id}/{upload_date}/{test_id}/images/{HHMMSSffffff}_image_0.png
  neetTestGenerator/{user_id}/{upload_date}/{test_id}/images/{HHMMSSffffff}_image_1.png

PDF:
  neetTestGenerator/{user_id}/{upload_date}/{test_id}/pdfs/file.pdf

upload_date is YYYY-MM-DD (UTC) — every upload for a given user on a given day lands under the same date folder, making the bucket browsable by day. Image filenames are prefixed with a microsecond-precision timestamp (HHMMSSffffff) so that listing the images/ folder sorts chronologically even though multiple images in one detection upload concurrently; the original index is kept as a suffix tiebreaker. The bucket is mldatabase (ap-south-1).

How Files Are Sent to the Model

file_typeFlow
image Upload to S3 → generate presigned URL → send as an image content block
pdf Upload to S3 (permanent storage). Gemini path (default): send the presigned S3 URL directly. OpenAI path: additionally upload to OpenAI Files API and send by file_id.

Range Logic

Applied in the API layer after the detector returns 9 raw counts (one per difficulty × question type). The detector returns raw counts only — range computation happens in code (api/detect.py:_compute_range).

count >= 10  →  min = count - 5,  max = count
count  < 10  →  min = max(0, count - 2),  max = count
count == 0   →  {count: 0, min: 0, max: 0}

Example output:

easy.mcq   = {count: 22, min: 17, max: 22}
medium.ar  = {count:  7, min:  5, max:  7}
hard.mtc   = {count:  3, min:  1, max:  3}
easy.ar    = {count:  0, min:  0, max:  0}

Section 05

Generator API

Student has reviewed the detector results and set their preferences. This API accepts the job, puts it on SQS, and returns a test_id immediately. An ECS worker processes it in the background. The frontend polls for status every 2 seconds.

Async SQS Queue ECS Worker Mixed Tests Frontend Polling

Mixed Tests — the components[] field

A single test can combine several question_type × difficulty combinations under one test_id — e.g. easy MCQ + hard Assertion-Reason + easy Match-the-Column, all delivered as one test the student attempts in one sitting. A normal, single-type test is simply a components list with one entry — the request shape never changes between the two cases.

"components": [
  {"question_type": "mcq",              "difficulty": "easy",   "question_count": 5},
  {"question_type": "assertion_reason",  "difficulty": "hard",   "question_count": 3},
  {"question_type": "match_the_column",  "difficulty": "easy",   "question_count": 2}
]

There is no client-facing top-level question_count — the server computes it as the sum across all components, purely for the total-cap check (1–100) and for display on the Jobs row.

API Input

{
  "user_id":          "user-123",
  "subject":          "biology",
  "medium":           "english",
  "components": [
    {"question_type": "mcq", "difficulty": "hard", "question_count": 10}
  ],
  "file_reference":   "s3://mldatabase/neetTestGenerator/user-123/2026-07-03/abc-123/pdfs/file.pdf",
  "file_type":        "pdf",
  "source_test_id":   "abc-123",
  "test_series_name": "Biology Hard Test",
  "plan":             "free"
}

Prompt Folder Structure

One file per (subject / language / type / difficulty) combination. Adding a new subject means creating a folder — no code changes needed. The selector auto-discovers at startup by scanning for metadata.json.

prompts/
  schemas/
    mcq.txt  mcq_hard.txt  ar.txt  mtc.txt  mtc_hard.txt   ← shared JSON output schemas
  answer_prompt.txt              ← single system prompt covering answer evaluation for all types

  biology/
    metadata.json
    base_template.txt            ← shared/English default outer wrapper
    latex_block.txt
    difficulty_extras.txt
    english/
      mcq/  assertion_reason/  match_the_column/
        prompt_easy.txt  prompt_medium.txt  prompt_hard.txt
        checklist_easy.txt  checklist_medium.txt  checklist_hard.txt   ← merged into the
                                                                          final prompt, not sent separately
    hindi/
      base_template.txt  latex_block.txt  difficulty_extras.txt   ← full native-language override
      metadata.json
      mcq/  assertion_reason/  match_the_column/  ...

  chemistry/
    english/  ...
    hindi/  ...
Language override pattern base_template.txt, latex_block.txt, and difficulty_extras.txt are read from {subject}/{language}/ first if present (full native-language prompt, no English boilerplate mixed in); otherwise the shared {subject}/ root file is used. This is how Hindi got fully-localized prompts without touching English.

PDF Handling — Topic-Based Chunking, Shared Across Components

PDFs are split into topic-based chunks using an LLM — not by fixed page count. Topic detection runs once per job, shared across every component in a mixed test; each component then independently distributes its own requested count across those same topics.

Step 1 — Topic Detection (LLM call, once per job) Upload full PDF to OpenAI Files API → file_id LLM identifies topics with page ranges and estimates question density per topic Step 2 — Per-component distribution For each component in job.components: distribute_questions(topics, component.question_count) → density-weighted, every topic gets at least 1 question where possible Step 3 — Flatten into one work list across ALL components mcq_easy_chunk_0, mcq_easy_chunk_1, ar_hard_chunk_0, mtc_easy_chunk_0, ... Step 4 — Generation (parallel across chunks AND components) ThreadPoolExecutor(max_workers=4) — one thread per (component, chunk) pair Each chunk: extract those pages → upload just that slice → generate_chunk() using that component's own type/difficulty prompt → delete upload Step 5 — Merge, dedup, validate, save All components' questions merge into ONE list dedup_questions() — Jaccard similarity, removes near-duplicates from page overlap Type-specific validators route by each question's own type/difficulty create_test() writes the merged, mixed-type list to NeetTestGenerator_Test

Batch Keys — Component-Prefixed

Every batch entry in batch_processing_detail is prefixed by its component's abbreviation and difficulty, so per-component progress is visible even inside a mixed test:

mcq_easy_chunk_0, mcq_easy_chunk_1        ← from the {question_type: mcq, difficulty: easy} component
ar_hard_chunk_0                           ← from the {question_type: assertion_reason, difficulty: hard} component
mtc_easy_chunk_0, mtc_easy_chunk_1        ← from the {question_type: match_the_column, difficulty: easy} component

Retry Logic Per Batch

Each batch gets a maximum of 3 attempts before being marked as failed.

Attempt 1 → fails → wait 2s → retry
Attempt 2 → fails → wait 4s → retry
Attempt 3 → fails → mark batch as failed, record error_message
OutcomeAction
All batches succeedstatus = Done — return all questions
Some batches fail, some succeedstatus = Partially Failed — return successful questions + message
All batches fail / job errors before any contentstatus = Failed — do not delete SQS message, let SQS retry

SQS Retry — Job Level

All batches fail (or the job throws before generation starts) ↓ Worker does NOT delete SQS message ↓ SQS visibility timeout expires (5 minutes) ↓ SQS re-delivers → ECS worker picks it up again ↓ Worker reads job status — already "Failed" → logs and exits without reprocessing ↓ After SQS maxReceiveCount is exhausted: ↓ SQS sends the message to the Dead Letter Queue (DLQ)
Idempotency process_message() always re-reads the job's current status before doing any work: Done/Partially Failed → delete the message, nothing to do. Failed → leave the message alone, let SQS's own retry/DLQ machinery run. This is what made a message that got redelivered after its underlying job row was deleted (during our schema testing) self-clean safely — the worker just logged job_not_found and deleted the message.

Full ECS Worker Flow (worker/main.py)

ECS worker: sqs.receive_message(WaitTimeSeconds=20, VisibilityTimeout=300, MaxNumberOfMessages=1) ↓ Read job details from DynamoDB by test_id ↓ Already Done/Partially Failed? → delete SQS message, done. Already Failed? → leave message alone (let SQS retry/DLQ), done. ↓ update_job_status(IN_PROGRESS, retry_count=ApproximateReceiveCount) ↓ image job → for each component: generate_chunk() once against the presigned URL pdf job → detect_topics() ONCE, shared across all components → for each component: distribute_questions() over the same topics → flatten into one work list across all components' chunks → ThreadPoolExecutor(4) runs them all in parallel ↓ Merge all components' questions → dedup_questions() → type-specific validators ↓ Determine outcome: 0 generated → Partially Failed some but not all → Partially Failed all requested → Done everything failed → Failed (do not ack SQS) ↓ create_test() → writes merged questions to NeetTestGenerator_Test complete_job() → writes final status/count to NeetTestGenerator_Jobs record_test_generated() → increments the user's usage counters (only now, post-completion) _enqueue_answers(test_id) → pushes to NeetTestGeneratorAnswer queue ↓ delete_job_progress(test_id) (Redis cleanup) Done/Partially Failed → delete SQS message Failed → do NOT delete SQS message (SQS will retry)

Frontend Polling Flow

Submit job → receive test_id ↓ Poll GET /status/{test_id} every 2 seconds ↓ Pending → "Preparing your test..." In progress → "Generating questions... (3 of 4 batches done)" Done → stop polling → show test → start polling GET /answers/{test_id} Partially Failed → stop polling → show test + warning message Failed → stop polling → show error + retry button
Section 06

Answer Generation Pipeline

After question generation completes (status = Done or Partially Failed), the system automatically generates correct answers as a separate, independent pipeline. Questions are delivered to the student the moment they are ready — answer generation runs in the background with zero impact on question delivery latency.

Async Separate SQS Queue Separate Worker Independent Retry

Answers live in NeetTestGenerator_Test, not Jobs

Earlier this stored a final_answers list and answers_status field directly on the Jobs row. That has moved: correct_answer is now a field directly inside each question object in NeetTestGenerator_Test.questions[] — there is no separate parallel answers list anywhere. answers_status also now lives on the Test row, not the Jobs row, since answers are test content, not pipeline state.

Why a Separate Queue and Worker?

  • Zero overhead for questions — status=Done is set and the question SQS message is deleted before answer generation starts.
  • Independent retry — if answer generation fails, it retries independently without touching the already-saved questions.
  • Independent DLQ — answer failures go to their own dead letter queue.
  • Independent scaling — the answer worker can scale separately from question generation.

Architecture Flow

Question Worker (worker/main.py) ... generates questions, writes NeetTestGenerator_Test with each question's correct_answer = None and answers_status = "Pending" ... Enqueues { test_id } to NeetTestGeneratorAnswer SQS queue Deletes its own SQS message ← student sees questions immediately ↓ Answer Worker (worker/answer_worker.py) Receives { test_id } Reads the Test row — if answers_status == "Done", delete message, exit (idempotency) update_answers_status(test_id, "Processing") Loads questions from NeetTestGenerator_Test (not Jobs) Strips to slim fields: question_id, question_type, question_text, options Batches 20 questions per LLM call (text-only, no file upload) save_answers() merges each {question_number, correct_answer} directly into questions[question_number - 1].correct_answer via a targeted UpdateExpression answers_status = "Done" Deletes answer SQS message

Answer Prompt Architecture

The answer worker uses a single system prompt (prompts/answer_prompt.txt) that covers all question types. The model evaluates each question independently and returns [{question_id, correct_answer}] — question_id here is the LLM-facing protocol field name; the worker maps it to question_number when merging into the Test row.

Question TypeEvaluation Rule
MCQ easy / mediumIdentify the single correct option
MCQ hard — multiple_correctDetermine which statement numbers are true, match to the option listing exactly those
MCQ hard — identify_incorrectFind the option stating a false fact
MCQ hard — sequence_orderDetermine the correct sequence, match to the option stating it
MCQ hard — true_falseClassify each statement, match to the option with that T/F pattern
Assertion-ReasonEvaluate Assertion and Reason truth independently, then whether Reason explains Assertion
Match the ColumnDetermine the correct pairing, match to the option stating that sequence

Daily Reset — Lazy, IST, No Cron

Every counter update first compares the IST (Asia/Kolkata) date-part of updated_at to today's IST date. If they differ, all four *_today fields are zeroed before applying the new update — no scheduled job needed, and correct the moment a user makes their next request past midnight IST. (Trade-off: a row for a user who is inactive on a given day still shows the previous day's numbers if read directly, e.g. by an admin dashboard — acceptable since nothing currently needs a cross-user "today" aggregate at arbitrary read time.)

question object shape

{
  "question_number":  1,
  "question_type":    "MCQ",              // uppercase — MCQ | ASSERTION_REASON | MATCH_THE_COLUMN
  "difficulty":       "hard",             // this question's own difficulty (mixed tests can vary per question)
  "question_category": "sequence_order",  // MCQ-hard only, free text (not an enum)
  "question":          "[latex/text of the question]",
  "answer_options":    {"a": "...", "b": "...", "c": "...", "d": "..."},
  "correct_answer":    "a"                // null until the answer worker fills it in
}

Every question type shares this exact shape, including Match-the-Column — the raw LaTeX table is stored as-is in question for rendering; no separate parsed column structure is persisted (a validator briefly parses it in-memory pre-save to catch duplicate Column-II entries, then discards the parsed form).

Section 08

Redis — Temporary State During Processing

Redis holds live per-chunk progress while a job is running, so the status endpoint doesn't need to hit DynamoDB on every poll. When the job finishes, final state is committed to DynamoDB and the Redis key is deleted.

Key:   "test:{test_id}"
TTL:   REDIS_JOB_TTL (default 3600s)

Value (hash): {
  "mcq_easy_chunk_0": { "trace_id": "...", "status": "processing" },
  "mcq_easy_chunk_1": { "trace_id": "...", "status": "done"       },
  "ar_hard_chunk_0":  { "trace_id": "...", "status": "pending"    }
}

All Redis operations are no-ops if Redis is unavailable — graceful degradation, generation still completes, only live progress display is lost.

Adaptive-Test Integration

Deployment is one API service + two worker processes, unchanged from the original design — include_router() mounts all test-generator routes into the shared adaptive-test FastAPI app, one Swagger at /docs. See the repository's deployment docs for the current supervisord/ECS configuration; endpoint paths now use {test_id} in place of {job_id}/{detection_id} throughout:

/test-generator/detect            → POST, SSE stream, returns test_id
/test-generator/generate          → POST, accepts components[], returns a NEW test_id
/test-generator/status/{test_id}  → GET, poll for completion
/test-generator/answers/{test_id} → GET, returns answer key
